# 增量更新与自动更新 · 设计方案

> 日期：2026-11-21 · 状态：**已实施（①②③ 步完成，④ 的离线包/旧版本清理也做了）**
> 相关：[ADR-0006 版本目录式更新器](../adr/0006-version-dir-updater.md)、[运维手册 §5 更新与回滚](../ops/运维手册.md)
>
> 实施记录见文末 [§18](#18-实施记录2026-11-21)；与原方案的差异集中在那一节。

## 0. 结论先说

**不是「一个更新器」，是四个相互独立的更新对象，各自用不同的机制。**

| 对象 | 体积 | 更新机制 | 为什么 |
| --- | --- | --- | --- |
| 外壳（Electron 主进程 / 托盘 / 引导） | 小，一年变几次 | **不自动更新**，随安装包走 | 它要能在内核坏掉时把界面拉起来；自己改自己 = 失去救援能力 |
| 内核 + Web + 契约（`dist/` + `build/web`） | 增量 **2~4 MB** / 全量 61 MB | **文件级增量**，落到新版本目录再切指针 | 一次发版只变 `main.dart.js` + 几十个 `.js`，全量 551 MB 的安装包 99% 是永远不变的二进制 |
| PC / Android 客户端 | 30~45 MB | **全量安装**，登录时检查 | 增量省 20 MB，复杂度翻倍，不划算（§8.6） |
| 模型 / ffmpeg / llama / transmission | 292 MB ~ 1 GB | **独立资产**，按内容哈希校验，坏了才重下 | 不参与版本号，永远不该被更新流程碰 |

三端的默认行为（已定）：

- **服务端**：默认**不自动更新**——不轮询、不下载、不安装，只在有人打开界面时被动查一次（§13.2）
- **客户端**：**登录时检查一遍**，发现新版本只亮红点，用户点了才下载安装（§8.1）
- **客户端不做增量**，服务端直接上增量，不做「全量过渡版」（§14）

网络部分：**一份签名清单 + 四个源**（局域网服务端 → **GitCode** → GitHub → Gitee）。
GitCode Release 单文件 2 GB、总容量不限、免备案免费用，551 MB 的服务端全量包直接放它上面；
Gitee 只有 100 MB 上限，只放清单、客户端包和 3 MB 的增量包。**整套分发成本 0 元，不需要买 OSS。**

下面逐条展开。

## 1. 现状实测（决定方案的几个硬数字）

| 项 | 实测值 | 影响 |
| --- | --- | --- |
| 服务端安装包 | **551 MB**（`ColaNasOs-Server-1.3.13-Setup.exe`） | 走全量 = 国内用户下 10~60 分钟 |
| 服务端解压后 | 约 1.1 GB（electron + models 292 MB + llama 102 MB + ffmpeg 177 MB） | 磁盘要留 2 个版本余量 |
| `apps/colanas_os/build/web` | **53 MB** | 其中 `canvaskit/` 37 MB、`fonts_fallback/` 4.9 MB **永不变化** |
| `main.dart.js` | 5.82 MB → brotli q11 **1.22 MB**（实测 8.6 s） | 每次发版必变的那一块，压缩后只有 1.2 MB |
| `dist/`（内核编译产物） | 7.05 MB / **543 个文件**，542 个 < 256 KB | 不能逐文件下载（543 个请求在弱网必挂），要打包 |
| `contracts/` | 1.6 MB | 参与版本清单 |
| PC 客户端 | setup 30 MB / 便携 zip 39 MB / 解压 91 MB | 全量更新成本可接受 |
| Android 客户端 | APK 45 MB（arm64 / TV 各一） | 同上 |
| 现有更新器 `kernel/updater.ts` | 269 行，`versions/D<N>` + `manifest.json`(sha256) + ed25519 + `current.json` 指针 | **地基已经打好**，缺的是网络下载、差分组装、运行时接线、界面 |
| 运行时 | 内核从 `app.asar` 里 fork（`electron/main.ts` → `dist/electron/kernel-host.js`） | **这是当前无法增量的根本原因**，必须先拆 |

**推论**：一次常规发版真正变化的字节 = `main.dart.js`(1.22 MB) + 变化的内核文件(压缩后 0.2~1.5 MB) + 零星 assets ≈ **2~4 MB**。
对比 551 MB，**压缩比 140~270 倍**。这个收益足够支撑「拆壳」的改造成本。

## 2. 目标与非目标

**目标**
1. 服务端增量更新：下载 2~4 MB，40 秒内完成切换；失败自愈、可一键回滚；**默认不自动安装**（用户点了才动）。
2. 客户端**登录时检查一遍**，三端（PC / Android / TV）都能自己完成更新。
3. 默认走 GitCode，实测变慢自动切 GitHub，用户不用管源。
4. 完全断网的 NAS 也能更新（U 盘放包）。
5. 所有下发的产物可验签，篡改即拒绝。

**非目标**
1. 不做灰度百分比（个人项目用户量不存在统计显著性，用「延迟发布 + 手动检查」代替）。
2. 不做 Electron 主进程的热更新（ABI 一变，原生模块全废）。
3. 不做 P2P / BT 分发更新包。
4. 不做二进制级 bsdiff（理由见 §3-D2）。
5. 不做客户端增量更新（理由见 §8.6）。
6. 不做「全量更新过渡版」——直接上增量，全量只作为增量失败的兜底路径（§14）。

## 3. 五个结构决策

### D1 · 壳与内核必须分离，壳做到「薄到不需要更新」

**现状**：`electron/main.ts` 里 `utilityProcess.fork(path.join(__dirname, 'kernel-host.js'))`，`__dirname` 在 `app.asar` 内。整个应用是一个不可分割的整体，改一行代码就得重装 551 MB。

**决策**：壳只保留四件事——找 `current.json`、fork 内核、托盘/开窗、执行更新。所有业务代码 + Web + 契约移到 `<dataDir>/versions/D<semver>/`。

```
ColaNasOs.exe (壳)
  └─ 读 %APPDATA%\colanas_os_server\versions\current.json
       └─ fork <dataDir>\versions\D10314\electron\kernel-host.js
```

**硬约束（必须写进注释，否则以后会踩）**：
- 版本目录里的代码不能 `require` 安装目录 `resources/` 之外的东西；
- `better-sqlite3` / `node-pty` / `onnxruntime-node` 这些原生模块按 **Electron ABI** 编译，**Electron 大版本不变就不能换**。所以：**Electron 升级 = 必须发新壳 = 走全量安装包**。这条边界要写在 `kernel-host` 顶部。
- 原生模块与 `node_modules` 固定在 `<dataDir>/runtime/node_modules/`，由壳打包时释放一次，不随版本目录走。版本目录里的 `require('better-sqlite3')` 靠 `NODE_PATH` 指向它。

**收益**：内核/Web 的更新彻底独立；壳坏了也只是「拉不起界面」，不会把版本目录搞坏。

### D2 · 用「硬链接 + 只替换变化文件」代替二进制 diff

新版本目录的组装方式：**从旧版本目录逐文件 `fs.linkSync`（NTFS 硬链接，同一卷内 O(1) 且不占空间），再把清单里哈希变了的文件 `unlink` 后写新内容**。

| 方案 | 增量大小 | 复杂度 | 失败面 |
| --- | --- | --- | --- |
| bsdiff / zstd --patch-from | 最小（~1 MB） | 高：要为每个文件维护历史 patch，跨版本组合爆炸 | patch 生成/应用都要原生依赖 |
| **硬链接 + 文件级替换** | 2~4 MB | 低：只需 sha256 比对 | 只有「写文件」一种操作 |
| 整包解压覆盖 | 551 MB | 最低 | 中途失败即损坏 |

**为什么不选 bsdiff**：真正每次必变的是 `main.dart.js`（已是 minified JS，brotli 后 1.22 MB）；它下面 37 MB 的 canvaskit、4.9 MB 字体、292 MB 模型的字节**一个都不变**——硬链接直接省掉，根本不需要 diff 算法。为剩下的 1.22 MB 引入 patch 工具链不划算。

**两个必须记住的坑**：
1. **硬链接不能原地写**。同一份数据两个目录共用，`fs.writeFileSync` 会同时改掉旧版本 → 必须 `unlinkSync` 再 `copyFileSync`。（`install()` 现在用 `cpSync`，不涉及这个；新的组装函数必须显式处理。）
2. **跨卷 `fs.linkSync` 会 `EPERM`**。`dataDir` 和 `versions/` 总是在同一卷，但如果用户把 `versions/` 指到别的盘，必须降级成 `copyFileSync` 并打日志。

### D3 · 传输压缩统一用 brotli，不用 zip/tar.gz

- Node 内置 `zlib.brotliCompress`，零依赖；q11 在 5.82 MB 上 8.6 s，CI 完全可接受。
- 比 gzip 小 25%（1.22 MB vs 1.62 MB 实测）。
- **按文件压缩而不是打包后压缩**：大文件单独一个 `.br`（可 `Range` 续传、可并行），小文件打成一个 `bundle.tar` 再压（543 个请求在弱网必挂，见 §1）。

阈值：单文件 ≥ 256 KB 单独走，其余进 bundle。按实测，`dist/` 里 542/543 个文件 < 256 KB —— 打包后只剩 1 个文件，加 web 侧大文件（`main.dart.js`、几个 assets）总共约 5~10 个请求。

### D4 · 签名在「清单」这一层，一次签全量

两层校验，各司其职：

```
update.json                      ← ed25519 签一次，覆盖所有组件、版本、sha256、字节数
  ├─ files[].sha256              ← 传输完整性（断点续传拼错、镜像截断）
  └─ manifest-D10314.json.sig    ← 版本目录级签名（文件清单整体，防「悄悄少一个文件」）
```

公钥**编译进**客户端与服务端（`kernel/update/pubkey.ts` 常量），不通过网络下发。私钥只在发布机 / CI secret 里。`update.json.sig` 与 `update.json` 分两个文件放，签名和内容不混在同一个 JSON 里（避免「签名覆盖自己」的鸡生蛋问题）。

### D5 · 客户端不直连公网，走服务端代理 + 局域网优先

客户端已经有「连哪个服务端」的概念，直接复用：客户端只问服务端 `GET /api/v1/system/update/check?component=client_pc`，服务端返回清单 + **自己缓存过的资产 URL**。

好处：
- 客户端不需要硬编码 GitCode/GitHub 地址，换源只改服务端；
- 局域网内 `192.168.x.x:7788` 下载 = 满速，国内公网怎么烂都不影响；
- 服务端本来就是常开的，天然是一个更新缓存节点；
- 服务端自己也用同一份清单，逻辑只写一次。

## 4. 目录布局

**安装目录**（卸载才动，更新不碰）
```
%LOCALAPPDATA%\Programs\ColaNasOs\
  ColaNasOs.exe              壳（冻结，极少更新）
  resources\
    tray.png / icon.ico
    runtime\node_modules\    原生模块（按 Electron ABI，随壳）
```

**数据目录**（更新只动 `versions/`）
```
%APPDATA%\colanas_os_server\
  versions\
    D10313\  D10314\         每个版本一个完整可运行目录
    current.json             { "id": "D10314" }   原子切换
    .staging-D10314\         下载/组装中的临时目录（失败直接删）
  manifest-cache\            D10314\manifest.json + .sig
  assets\                    模型/ffmpeg/llama（按内容哈希寻址，不参与版本）
  update\
    inbox\                   离线包投放目录（U 盘拷进来）
    cache\                   下载缓存（可续传，7 天过期）
  backup\
    db-snapshots\D10313.db   切指针前的 DB 快照
  boot.json                  { id, attempts, healthyAt }  崩溃自愈用
  colanas.db  logs\  thumbs\ ...
```

**版本目录内部**
```
D10314\
  manifest.json              { version, algo, files:{rel:sha256}, signature }
  electron\kernel-host.js
  kernel\...                 dist 编译产物
  web\index.html  main.dart.js  canvaskit\...
  contracts\locales.json
  sidecars\
```

注意 `manifest.files` **只覆盖版本目录内的文件**（约 61 MB、几百个文件）。模型/ffmpeg 不进来——否则每次校验要读 2.7 GB，启动慢到不可接受。

字段取舍说明：

- **`from` 是白名单不是相邻版本**。只对列出的基线版本发增量；不在列表里 → 直接走全量。这样发版时保留最近 3 个基线，跨更远版本的用户走全量，避免维护 N×N 的 patch 矩阵。
- **`version` 是整数**（`major*10000 + minor*100 + patch`，1.3.13 → 10313），直接喂给现有 `Updater`，`D10313` 的命名规则不用改（`padStart(3)` 不截断）。
- **`br` 是可选的压缩形态**。没有 `br` 就用原始文件（`Accept-Encoding` 已在外层处理时）。客户端优先取 `br`，不支持的旧客户端走原文件。
- **`urls` 是数组**，顺序 = 优先级，但客户端会重新测速排序（§9）。

## 6. 服务端增量更新流程

由内核发起（内核有网、有磁盘、知道任务队列空不空），**壳只负责在最后重启**——因为内核无法替换自己正在跑的文件。

```
[1] 检查     默认**被动**：有人访问界面（Web 打开 / 客户端登录问 check）且缓存 > 6h 才真查一次
             可选主动：设置里打开「自动检查」才 6h 轮询（默认关，§13.2）
             用户手动点「检查更新」永远走这里，忽略节流
             GET update.json（走 proxyFetch，尊重系统代理）
             版本比较：semver > 当前 且 version > 当前 且 不在 skip 名单
[2] 预检     disk.free >= delta.size * 2 + 500MB     否则拒绝，提示用户
             任务队列 idle（转码/索引/人脸在跑就等，或让用户选「现在更新」）
             electron 版本 >= minShell
             到这一步只算「预检」，**不下载**——等用户点「立即更新」才进 [3]
[3] 下载     按 §9 选源 → 写 update\cache\D10314\*.part
             Range 续传；每 64KB 落盘一次进度
             流式 brotli 解压（先写 .part，hash 校验通过才 rename）
[4] 校验     br.sha256 → 解压 → 原文件 sha256 == files[].sha256
             update.json.sig ed25519 验签（公钥内嵌）
[5] 组装     从 current 目录逐文件 linkSync 到 .staging-D10314\
             变化文件：unlink → copyFileSync（跨卷降级 copy 整目录）
             目录本身不能硬链接，逐层 mkdir
[6] 全量校验  拉 manifest.json + .sig，逐文件 sha256（61 MB，实测 < 1 s）
             注入 web\version.json（Flutter 产物自带，用来让浏览器判断新旧）
[7] DB 快照   UPDATE 前：sqlite `VACUUM INTO backup\db-snapshots\D10313.db`
             （在线备份，不用停库；比复制 db+wal 安全）
[8] 切换     atomic: 写 versions\current.json.tmp → rename
             fsync 目录项（Windows 上靠 MoveFileEx 保证，Node 的 rename 已是原子）
             写 boot.json { id: D10314, attempts: 0, healthyAt: null }
             请求壳重启 → 壳 kill 内核 → fork <versions>\D10314\electron\kernel-host.js
[9] 确认     内核起来后 /health 200 且 DB 迁移完成 → boot.json.attempts = -1（健康）
             壳在 3 分钟内没收到健康信号 → 下次启动自动回滚
```

**为什么要 `VACUUM INTO` 而不是复制 `.db`**：库开着 WAL，复制出来的文件可能缺最后几个事务。`VACUUM INTO` 是 SQLite 官方的在线备份，产出一个自洽的单文件。

**为什么切指针前才做快照**：更早做会丢失「下载期间新写入的数据」；更晚做就来不及了。

## 7. 崩溃自愈（这一段最容易漏，但决定「敢不敢自动更新」）

`boot.json` 是自愈的唯一依据：

```json
{ "id": "D10314", "attempts": 2, "firstBootAt": 1795000000000, "healthyAt": null }
```

壳启动时的逻辑：

```
读 boot.json
  ├─ healthyAt != null            → 正常启动
  ├─ id != current.json.id        → 重置（指针变了）
  ├─ attempts >= 3                → 判定新版本坏 → activate(上一版) + 恢复 DB 快照 + 保留日志
  └─ 否则 attempts++ → fork 当前版本，等健康信号
```

「健康」的定义要严格：**HTTP `/health` 200 && 迁移表最新 && 内核自己上报 listening**。只是进程活着不算——内核可能卡在迁移死循环里，反复重启也永远不健康。

回滚会**丢掉更新之后写入的数据**（快照是更新前的）。这一点必须诚实告知：回滚对话框写清楚「将回到 11-21 02:00 的数据」，并把当前库另存为 `db-snapshots/rollback-<时间戳>.db` 供事后捞数据。

## 8. 客户端更新（PC / Android / TV / Web）

### 8.0 三端总览

| 端 | 更新方式 | 包体 | 用户动作 | 生效时机 |
| --- | --- | --- | --- | --- |
| **PC Windows（安装版）** | 全量静默安装 | 30 MB | 点一下「立即更新」 | 装完自动重启客户端 |
| **PC Windows（便携版）** | 全量 zip 自替换 | 39 MB | 点一下「立即更新」 | 解压完写指针，重启生效 |
| **Android / Android TV** | 全量 APK | 45 MB | 点「下载」→ 系统装 | 系统安装器接管 |
| **Web** | 随服务端更新 | — | 刷新页面 | 立即 |

四个共同点：

1. **检查时机统一是「登录成功后」**（用户明确要求，见 8.1），不做后台轮询；
2. **下载前不打断正在做的事**——PC 在播放音乐时不重启、Android 不在前台下载大包；
3. **所有包都验 sha256 + 清单签名**，装之前拒绝任何不一致的产物；
4. **更新失败不影响已装版本**，最差的结果是「这次没更新」，不是「应用打不开」。

### 8.1 什么时候检查（登录时检查一遍）

用户明确要求：**客户端在登录时检查一遍**。落成五条规则：

| 时机 | 是否检查 | 说明 |
| --- | --- | --- |
| **登录成功那一刻** | ✅ 必查 | 拿 token 后立刻 `check`，与首页数据并行发出，不阻塞进主页 |
| 冷启动但未登录（记住登录态的自动登录） | ✅ 查 | 用本地缓存的清单，先比版本，登录后再取详情 |
| 同一会话内切页 / 切应用回来 | ❌ 不查 | 会话内只查一次，避免每进一个页面打一个请求 |
| 同一设备 6 小时内重复登录 | ❌ 不查 | 记录 `lastCheckAt` 到本地设置，6h 内直接用缓存结果 |
| 用户点「设置 → 关于 → 检查更新」 | ✅ 强制查 | 忽略节流，带 `?force=1` |

**不做后台定时轮询**：客户端是「打开才用」的，登录时查一次覆盖 99% 场景；服务端是常驻的，由它自己按 6h 查（§13）。

接口只一个，三端共用：

```
GET /api/v1/system/update/check
    ?component=client_pc&current=1.3.13&platform=windows-x64&channel=stable
→ { hasUpdate, latest: { semver, version, notes, minServer },
    assets: [ { kind: "setup" | "portable" | "apk" | "apk_tv",
                size, sha256, urls: [...] } ] }
```

`urls` 由服务端拼装：**局域网地址排第一**（服务端自己缓存的资产，`/api/v1/system/update/asset/...`），后面才是 GitCode / GitHub。客户端拿到就不需要知道自己连的是谁家的源。

### 8.2 PC Windows · 安装版（主路径）

**现有安装器的事实**（`tool/build-client-installer.js` 生成的 NSIS 脚本）：

- `RequestExecutionLevel user` → **不触发 UAC**，普通用户就能装
- `InstallDir "$LOCALAPPDATA\Programs\ColaNasOs 客户端"` → 安装目录**可写**
- `STOP_RUNNING_APP` 宏已在 Section 开头执行 → **静默安装会自己结束旧客户端**，不需要用户先退出
- `RMDir /r "$INSTDIR"` → 整个安装目录清空重装
- 用户数据在 `getApplicationSupportDirectory()`（`%APPDATA%\...`），**不在安装目录 → 不会被删**，服务器地址、登录态、音乐缓存全部保留

也就是说，**「静默覆盖安装」这条路现有的安装器已经具备 90% 的能力**，只差「装完自动把客户端拉起来」。

**流程（7 步）**

```
[1] 检查       登录成功 → check 接口 → 发现 1.3.14 → 设置页红点 + 一条 toast
[2] 用户确认   点「立即更新」→ 弹窗写明：约 30 MB / 会关闭并重启客户端 / 正在播放的音乐会停
[3] 下载       落 %TEMP%\colanas-update\Client-1.3.14-Setup.exe
               多源选速（局域网 → GitCode → GitHub）+ Range 续传
               进度条：已下载 / 总大小 + 速度；可暂停、可取消
[4] 校验       sha256 对比清单；不一致 → 删文件、换源重试一次
[5] 拉起安装   设 COLANAS_RELAUNCH=1，spawn:
               "Client-1.3.14-Setup.exe" /S
               客户端随即主动退出（给安装器让出 exe 句柄）
[6] 安装器     内部 STOP_RUNNING_APP（兜底）→ RMDir 旧目录 → 拷新文件
               → Section 末尾判断 COLANAS_RELAUNCH=1 → Exec "$INSTDIR\colanas_os.exe"
[7] 回来       新客户端启动，版本号已变；设置页清掉红点
```

**唯一需要改安装器的点**：`Section` 末尾加

```nsis
; 静默安装（/S）不会走完成页，需要显式把客户端拉起来
ReadEnvStr $0 "COLANAS_RELAUNCH"
${If} $0 == "1"
  Exec '"$INSTDIR\${APP_EXE}"'
${EndIf}
```

不改的话，静默安装完就停在「装好了但没启动」，用户会以为应用被卸载了。

**失败分支**

| 情况 | 处理 |
| --- | --- |
| 下载中断 / 校验失败 | 保留 `.part` 续传；两源都失败 → 提示「稍后重试」+ 打开下载页 |
| 磁盘不足 | 下载前检查 `%TEMP%` 剩余 > 2×包体，不足直接拒绝并提示 |
| 安装器返回非 0 | 提示「安装失败」+ 给出安装器日志路径 + 「手动下载」按钮 |
| 装完起不来 | 客户端启动时写 `lastBootVersion`；连续两次起不来 → 提示「重新安装」并提供上一版安装包链接 |
| 用户取消更新 | 立刻停止，删 `.part`，不影响当前运行 |

**回滚**：PC 客户端不做版本目录，回滚 = **重新装上一版**。所以发布时必须保留 **最近 2 个版本**的 setup 直链（清单里带 `previous` 字段，或者约定 URL 规则 `.../v1.3.13/Client-1.3.13-Setup.exe`）。装在 `%LOCALAPPDATA%` 的包，重装 30 MB 也就 10 秒，不需要更复杂的机制。

### 8.3 PC Windows · 便携版（zip）

便携版没有安装器，只能自替换。识别方式：安装目录不存在`Uninstall.exe`，或存在 `portable.marker`。

```
1. 下载 zip（39 MB）→ 解压到 <程序目录>\app\v1.3.14\（新目录，不污染当前）
2. 校验解压后的 colanas_os.exe 的 sha256（先 kill 自己的子进程，不 kill 自己）
3. 写 <程序目录>\app\current.txt = v1.3.14
4. 提示「重启后生效」，用户重启 → 引导 exe 读 current.txt 加载新目录
```

**Windows 的运行中替换限制**：正在运行的 `exe` 不能被覆盖或删除，但**可以被 rename**。所以便携版需要一个极小的引导器（`ColaNasOs.exe`，几十 KB）：

```
ColaNasOs.exe (引导器，几乎不变)
  └─ 读 app\current.txt → 启动 app\<ver>\colanas_os.exe
```

引导器自身要更新时才用 rename 技巧，概率极低。**这和 §3-D1 服务端「壳 + 版本目录」是同一个思路**，实现可以共用一份。

### 8.4 Android / Android TV

Android 不给普通应用静默安装的权限（那需要系统签名或设备管理器），只有一条路：**下载 APK → 交给系统安装器**。

```
[1] 检查    登录成功 → check?component=client_android
            比较 versionCode（不是 semver 字符串！Flutter 的 X.Y.Z+B 里 B 就是 versionCode）
[2] 提示    「发现新版本 1.3.14（45 MB）」，显示更新说明，两个按钮：立即更新 / 稍后
[3] 下载    自研下载器（复用 §9.4 的选源器），落 getExternalFilesDir()/updates/
            前台通知显示进度（Android 14 需要 FOREGROUND_SERVICE_DATA_SYNC 权限）
            支持断点续传；切后台继续，不强杀
[4] 校验    sha256 == 清单；
            再用 PackageManager.getPackageArchiveInfo(..., GET_SIGNING_CERTIFICATES)
            读新 APK 的签名，与自身签名比对 —— 不一致直接删包并报错（防钓鱼包冒充更新）
[5] 安装    FileProvider.getUriForFile → Intent(ACTION_VIEW)
            .setDataAndType(uri, "application/vnd.android.package-archive")
            .addFlags(FLAG_GRANT_READ_URI_PERMISSION | FLAG_ACTIVITY_NEW_TASK)
[6] 权限    首次会弹「是否允许安装未知应用」→ 引导跳到
            Settings.ACTION_MANAGE_UNKNOWN_APP_SOURCES + package: 本应用
[7] 兜底    国产 ROM 拦截（小米「安装未知应用」、华为「纯净模式」、OPPO/vivo 各自开关）
            → 检测到「没装成」就展示分步图文 + 「复制下载链接」按钮
```

**为什么不用 DownloadManager**：它不支持我们的多源选速与熔断，失败后无法换源重试，国产 ROM 上还会被省电策略掐断。自研下载器只有 100 行，但能复用同一套源选择逻辑。

**TV 版差异**：遥控器焦点必须在两个按钮之间可达；进度条要大字；安装确认页是系统 UI，遥控器方向键可用，无需额外适配。TV 端不做「自动下载」，45 MB 更该让用户决定。

**Android 的「不做」**：

- 不做增量（split APK / 差分包需要自建签名分发，收益 20 MB，不值）
- 不做后台静默安装（拿不到权限）
- 不做应用内自升级（会被 Play 政策与厂商商店规则卡）

### 8.5 Web

Web 是服务端产物，随服务端更新，**不需要独立更新器**。两个缓存坑：

1. `kernel/static-web.ts` 已经给 `cache-control: no-cache`，`index.html` 每次回源 → 新版本立刻生效。保持这个设置，**不要**为了性能改成 `max-age`，除非文件名带内容哈希。
2. 引导页已经主动 `unregister()` service worker 并清缓存（`docs` §74 记过这个坑）。更新后如果用户看到旧界面，提示条给一个「刷新」按钮（`location.reload(true)` 不靠谱，用带版本号 query 跳转）。

服务端更新完成后，已打开的浏览器标签页会拿到旧 `main.dart.js` → 接口契约不兼容时表现为「点了没反应」。所以服务端切版本后，**给所有在线 Web 会话推一条「已更新，请刷新」**（SSE / WebSocket 已有通道），比让用户自己发现强。

### 8.6 客户端为什么不做增量（明确回答）

| 理由 | 说明 |
| --- | --- |
| 收益太小 | 30 MB → 约 8 MB，只省 22 MB；而服务端增量省 548 MB，量级差 25 倍 |
| 故障面太大 | Windows 要处理 exe/dll 占用、rename、引导器；Android 要自建 split APK 签名。任何一步出错，结果是「应用打不开」而不是「这次没更新」 |
| 校验成本反而更高 | 增量要维护 `from` 清单矩阵（N 个客户端版本 × M 个新版本），全量只要一个 sha256 |
| 用户感知不到 | 30 MB 在 14 MB/s 下是 2 秒，在 1 MB/s 下是 30 秒——用户能接受 |

**例外**：如果以后客户端体积涨到 150 MB 以上（比如内置了模型），再按 §3-D2 的硬链接方案给 PC 端做增量。现在不做。

### 8.7 版本兼容矩阵

客户端和服务端可以不同版本（客户端连局域网服务端、也可能连别人家的）。清单里带 `minShell` 和客户端的 `minServer`：

| 组合 | 行为 |
| --- | --- |
| 客户端 < 服务端 | 正常，提示「有新客户端」 |
| 客户端 > 服务端 | 正常，提示「服务端可更新」 |
| 客户端 API 版本 > 服务端支持的 | 调用返回 `426 Upgrade Required`，界面提示更新服务端 |
| 服务端 `minShell` > 当前壳 | 拒绝内核更新，提示「需要重装服务端」（Electron 大版本变更） |
| 客户端 `minServer` > 服务端版本 | 登录页直接提示「服务端版本过低」，不进入主界面 |

### 8.8 客户端更新状态机

```
idle ──登录成功──> checking ──无更新──> idle
                      │
                   有更新
                      ↓
                  available ──用户点「稍后」──> idle（本地记住该版本已提示）
                      │
                  点「立即更新」
                      ↓
                  downloading ──失败──> failed（可重试 / 换源）
                      │
                   校验通过
                      ↓
                  installing ──失败──> failed
                      │
                   完成
                      ↓
                  done（PC 自动重启 / Android 交给系统 / 下次启动确认版本）
```

文案要求：**每个状态都有明确的一句话**，不出现「正在处理…」这种没有信息量的提示。失败时一定给出「下一步能做什么」（重试 / 换源 / 手动下载 / 复制链接）。

## 9. 国内网络（这一段决定「能不能用」）

### 9.1 源分层

| 源 | 放什么 | 为什么 |
| --- | --- | --- |
| **局域网服务端** `http://<lan-ip>:7788/api/v1/system/update/asset/*` | 服务端已缓存的资产 | 客户端的首选。局域网满速，且不消耗公网流量 |
| **GitCode Releases**（CSDN，后端华为云 OBS） | **全部资产**（551 MB 全量包 + 增量 + 清单） | **单文件 2 GB、总容量不限**。无需备案域名、无需付费。实测同类项目 14 MB/s。**这是国内主源** |
| **GitHub Releases** | 全量包 + 清单 | 国际源 + 代码与发布记录（CI 已经按 tag 发）。单文件 2 GB 软限制 |
| **Gitee Releases** | 清单 + 客户端包 + 服务端**增量包** | 国内备源。**单附件 100 MB 上限**（GVP 200 MB），551 MB 全量包放不上去 |
| （可选）自建 OSS + CDN | 全部资产 | 只在「要绑自己域名 / 要 CDN 边缘缓存」时才需要。非必需 |

**结论**：**不买 OSS 也能跑通全量分发**——GitCode 兜住 551 MB，Gitee 兜住清单和增量，GitHub 兜住国际访问。三源互相备份，成本 0 元。

**默认顺序（已定）**：`局域网 → GitCode → GitHub → Gitee`。GitCode 是国内默认源；实测速度掉到阈值以下（< 200 KB/s 持续 10 秒）就自动切 GitHub，不等用户察觉。这是「默认 GitCode，太慢用 GitHub」的落地形式。

### 9.2 国内分发平台能力边界（2026-11 实测/官方口径）

| 平台 | 单文件上限 | 总量 | 免费 | 备案域名 | 脚本发布 | 判断 |
| --- | --- | --- | --- | --- | --- | --- |
| **GitCode** | **2 GB** | 不限 | ✅ | 不需要 | ✅ `upload_url` 预签名 PUT | **首选主源** |
| Gitee | 100 MB（GVP 200 MB） | 仓库 1 GB | ✅ | 不需要 | ✅ v5 API | 只放清单/增量/客户端 |
| GitHub | 2 GB（>100 MB 建议 LFS） | 仓库 2 GB 建议 | ✅ | 不需要 | ✅ `gh release` | 国际源 |
| AtomGit（开放原子） | 接口结构与 GitCode 同源（`upload_url` + `x-obs-*`），附件限额未见公开口径 | — | ✅ | 不需要 | ✅ v5 API | 备胎，需实测 |
| 阿里云 OSS / 腾讯云 COS | 无 | 按量计费 | ❌（有试用） | **CDN 绑域名需 ICP 备案** | ✅ SDK | 要自定义域名时才用 |
| 七牛云 Kodo | 无 | 10 GB 免费存储 | ✅ 10 GB/月 CDN 流量 | **CDN 域名需备案** | ✅ SDK | 免费额度最慷慨的 OSS |
| 蓝奏云 / 123 盘 / 阿里云盘 | 100 MB~ | — | ✅ | — | ❌ 无稳定直链 | **不能用**（不能做自动更新） |

三个容易踩的点：

1. **Gitee 100 MB**：`ColaNasOs-Server-1.3.14-Setup.exe`（551 MB）放不上。分卷（`split -b 90M` → 7 片）技术上可行，但任何一片失败整个更新就废，体验比 GitCode 差一个数量级——**别走这条路**。
2. **国内 OSS/CDN 绑自定义域名要 ICP 备案**。不备案只能用 OSS 默认域名（`bucket.oss-cn-hangzhou.aliyuncs.com`），而阿里云对默认域名的 exe/apk 下载会强制 `Content-Disposition: attachment` 且有频次限制。所以「自建 OSS」真正的门槛不是钱，是**备案**。
3. **网盘一律不能用**：没有稳定直链、要登录、限速、会改文件名。自动更新的前提是「一个能 `Range` 请求的 URL」。

### 9.3 GitCode 接入要点

Release 附件走两步（预签名直传，不是 multipart 到 API 本体）：

```
1. GET https://api.gitcode.com/api/v5/repos/{owner}/{repo}/releases/{tag}/upload_url
        ?access_token=<PAT>&file_name=ColaNasOs-Server-1.3.14-Setup.exe
   → { url: "https://gitcode-release.obs.cn-south-1.myhuaweicloud.com/...",
       headers: { "x-obs-meta-project-id": "...", "x-obs-acl": "public-read",
                  "x-obs-callback": "...", "Content-Type": "..." } }

2. PUT <url>，**原样带上传回的 headers**（少一个 x-obs-* 就会 403）
```

- 下载直链：以 Release 页面「复制链接」为准（形如 `.../releases/download/<tag>/<file>`）；不要自己拼 CDN 域名，签名会过期。
- `access_token` 在 GitCode 个人设置里生成，权限给 `repo`。
- **ACL 要实测**：`upload_url` 返回的 `x-obs-acl` 可能是 `public-read` 也可能是 `private`。如果是 `private`，直链会 403，必须在发布后跑一次 `curl -I` 验证——这也是流水线里必须有「发布后回读」步骤的原因（§10.1）。
- GitCode 会自动镜像 GitHub 仓库（`gitcode.com/gh_mirrors/...`），但**不要依赖镜像发 Release**，自己 push 一遍最稳。
- 平台在国内，有内容合规审核；本仓库是 GPL-3.0 开源 NAS 系统，不涉及风险内容，但「发版被卡审核」要有心理准备，所以 GitHub 主链路不能停。

### 9.4 选源算法

```
候选 = [局域网(若在线) → GitCode → GitHub → Gitee]     ← 顺序即默认优先级
1. 第 1 个源直接开下，不预先测速（少一次往返）
2. 每 2 秒采样一次速度，维持滑动窗口（最近 6 秒平均）
3. 触发切换的三个条件，任一成立即熔断当前源：
     · 5 秒没有收到首字节
     · 最近 6 秒平均 < 200 KB/s
     · 连接被重置 / HTTP 4xx、5xx
4. 切换时带上已下载的 offset 续传，不从头再来；每个源最多试 2 次
5. 局域网源只用于「服务端已缓存的同一份资产」，缓存未命中直接跳过（不要让它回源转发，那比直连公网还慢）
6. 全部失败 → 指数退避（30s / 2min / 10min）→ 转「手动下载」入口
7. 成功的源按「资产 sha256」记进本地设置，下次同资产优先用它
```

**为什么不在下载前并发测速**：多一个 RTT，还要维护探针文件；边下边测更直接——反正真正的判据是「下载速度」，不是「握手延迟」。只有「当前源连不上」时才需要快速探下一个。

**为什么阈值是 200 KB/s**：551 MB 在 200 KB/s 下要 46 分钟，已经差到该换源；而 GitCode 正常是 5~14 MB/s，掉到这个数说明链路出问题了。

### 9.5 弱网的具体处理

| 问题 | 处理 |
| --- | --- |
| 大文件断流 | HTTP `Range` 续传，`.part` 文件 + `.part.json` 记录 offset/sha，重启进程可继续 |
| 小文件海量请求 | 打包成 bundle（§3-D3） |
| 运营商劫持 / DNS 污染 | 不依赖传输安全：所有产物 sha256 + ed25519 验签，被替换直接拒绝并换源 |
| 系统代理 | `kernel/proxy-fetch.ts` 已支持（`configureProxy` / `activeProxy`）；下载器统一走它，不直接用 `undici` |
| 公司网络限速 | 限流开关（默认不限制；设置页可设 2 MB/s），避免更新把用户正在看的视频搞卡 |
| 完全断网 | 离线包：放 `update\inbox\*.zip` → 设置页「从本地文件更新」（§10.3） |

### 9.6 成本

| 方案 | 成本 | 说明 |
| --- | --- | --- |
| **GitCode + Gitee + GitHub**（推荐） | **0 元** | 全部免费额度之内；GitCode 总容量不限，551 MB × N 个版本也不花钱 |
| 七牛云 Kodo | 0 元起 | 10 GB 存储 + 10 GB/月 CDN 流量免费，个人项目够；超了按 0.26 元/GB |
| 阿里云 OSS | 存储 ~0.25 元/月，流量 0.5 元/GB | 551 MB 一次全量下载 ≈ 0.28 元。**但要备案域名才能上 CDN** |

「值不值得自建源」的答案变了：**在没有自定义域名需求时，三个免费平台已经够用，不必花钱**。留 OSS 的位置只是为了将来接 CDN 做边缘加速。

## 10. 发布流水线改造

### 10.1 顺序不能错

```
build → gen → build-web → 打包(electron-builder / flutter) 
  → 组装版本目录(只含 dist + web + contracts + sidecars)
  → 生成 manifest.json + 签名
  → 对 from[] 每个基线生成增量包（bundle + br + 每个文件的 sha256）
  → 生成 update.json + update.json.sig
  → 上传资产（**GitCode 先传**，再 GitHub、Gitee）
  → 【最后】上传 update.json          ← 顺序错了就是「清单先到、包没传完」的 404 地狱
  → smoke：用 1.3.13 的真实目录跑一次「增量组装 + 校验 + 切指针」
```

**清单最后上传**是这条流水线唯一的铁律。为了防止人工失误，`update.json` 的路径加随机后缀（`update-<buildId>.json`），再由一个 `latest.json` 指向它——上传完成后再改 `latest.json`。

### 10.2 多平台发布

| 平台 | 做什么 | 认证 |
| --- | --- | --- |
| GitHub | `git push` + `gh release create v1.3.14` 上传资产（已有 CI 按 tag 触发） | `GITHUB_TOKEN`（已有） |
| **GitCode** | `git push gitcode main --tags` + v5 API 两步上传（`upload_url` → PUT）。**全量包走这里** | `GITCODE_TOKEN`（新建 secret） |
| Gitee | `git push gitee main --tags` + OpenAPI 创建 release、上传 ≤100 MB 附件 | `GITEE_TOKEN`（新建 secret） |
| （可选）OSS | `ossutil cp -r` | AK/SK |

每个平台都要带**发布后回读**：上传完 `curl -I` 每个 `urls[]`，确认 `200 + content-length` 与清单一致。少这一步，ACL 配错或分片没传完只会在用户端暴露成 404。

Gitee 侧的注意点：
- 需要先在网页上建仓库并完成实名，才能用 OpenAPI；
- `gitee-target-commitish` 默认 `master`，本仓库是 `main`，必须显式指定，否则 release 关联失败；
- 同一 tag 重复上传会覆盖同名资产（幂等，可重跑）；
- Gitee 有 API 限流，资产多时串行上传 + 重试。

### 10.3 离线包格式

给「内网 NAS 不给出网」的场景：

```
colanas-offline-1.3.14.zip
  update.json               （与线上同一份，签名字段一致）
  D10314/manifest.json  .sig
  D10314/kernel/...  web/...       （增量：只含变化文件；或全量目录）
  README.txt               （人读的说明）
```

服务端扫描 `update\inbox\*.zip` → 校验 → 走与在线完全相同的 [5]~[9] 步。**同一条代码路径**，不要为离线包写第二套逻辑。

## 11. 安全

| 威胁 | 防线 |
| --- | --- |
| 下载源被投毒 / 劫持 | `update.json` ed25519 签名 → 每个资产 sha256 锁死在签过名的清单里 |
| 中途替换单个文件 | 版本目录级 `manifest.json` 签名 + 逐文件 sha256 全量复核 |
| 降级攻击（喂旧版本利用已修漏洞） | `activate()` 默认拒绝降级；`from` 白名单；`releasedAt` 单调 |
| 重放（把旧清单挂回去） | 清单里 `version` 严格大于当前；`keyId` 不匹配则拒绝 |
| 解压路径穿越（`../../`） | 解压前校验每个 `path`：拒绝绝对路径、`..`、`:`、Windows 保留名（`CON`/`NUL`） |
| 私钥泄露 | `keyId` 版本化；客户端内置**新旧两把**公钥，可平滑轮换；私钥只在本机 / CI secret |
| 供应链（npm 依赖被投毒） | 已有 `npm run sbom` + `sbom.check`，发版前跑 |

**签名密钥的落地**：`*.pem` 已在 `.gitignore`。私钥建议放 `%USERPROFILE%\.colanas\deploy.pem`，发布脚本从环境变量 `COLANAS_SIGN_KEY` 读路径；CI 里用 secret 写临时文件，用完即删。

## 12. 失败矩阵

| 场景 | 现象 | 处理 |
| --- | --- | --- |
| 下载到 60% 断网 | `.part` 残留 | 保留 7 天，续传；过期清理 |
| 校验失败 | sha256 不符 | 删 `.part`，换源重下；两源都失败则报错并保留日志 |
| 组装中断电 | `.staging-D10314` 残留 | 启动时清理所有 `.staging-*`（超过 1h 的） |
| 切指针后起不来 | 3 次重启 | 自动回滚指针 + 恢复 DB 快照 + 保留 `logs/boot-fail-*.log` |
| 磁盘满 | `ENOSPC` | 预检拦截；组装中途失败则删 staging，不碰 current |
| 文件被占用（杀软/索引） | `EBUSY`/`EPERM` | 重试 3 次（间隔 500ms）；仍失败 → 中止，不切指针 |
| 硬链接跨卷失败 | `EPERM` | 降级整目录 `cpSync`，日志警告 |
| DB 迁移失败 | 内核起不来 | 同上，回滚 + 恢复快照 |
| 用户时钟错乱 | `releasedAt` 在未来 | 只用 `version` 比较，`releasedAt` 只做展示 |
| 服务端在跑转码 | 重启打断任务 | 预检 `queue idle`；强制更新时提示「N 个任务会重跑」 |
| Android 装不上 | 厂商拦截 | 兜底文案 + 复制链接 + 二维码 |

## 13. 更新策略（默认值）

### 13.1 三端开关

| 开关 | 服务端 | PC 客户端 | Android |
| --- | --- | --- | --- |
| 检查新版本 | **被动检查**（默认） | **登录时检查**（默认开） | **登录时检查**（默认开） |
| 自动下载 | 关 | 关 | 关（可选「仅 Wi-Fi 自动下载」） |
| 自动安装 | 关 | 关 | 关（系统也不允许静默装） |
| 通知 | 设置页红点 + 一次性提示 | 红点 + toast | 红点 + 通知 |

### 13.2 服务端：默认「不自动更新」

用户明确要求：**服务端默认关闭自动更新**。落成三条：

1. **不主动轮询**。没有开关打开时，服务端完全不发更新请求，NAS 在半夜不会自己联网。
2. **被动检查**：只要有人访问界面（Web 打开、客户端登录问 `check`），如果本地缓存超过 6 小时，就顺手真查一次并缓存结果。所以用户一打开界面就能看到「有新版本」，不需要任何定时器。
3. **不自动下载、不自动安装**。必须用户点。点了之后也是「下载 → 校验 → 等一个确认 → 才切版本」——因为切版本会重启内核，会打断转码 / 备份 / 做种。

给愿意「无感」的用户留一个开关：`设置 → 更新 → 自动检查（每 6 小时）`，开了才会主动轮询；再往上是 `空闲时自动安装`（检测到任务队列空闲 + 无播放会话才动手）。

「自动安装默认关」的理由：NAS 是常开设备，可能在跑备份/转码/做种；静默重启的代价比「用户晚两天更新」大。用户主动开了这个开关，就是明确授权了。

### 13.3 客户端：登录时检查一遍

- **登录成功 → 立刻检查**，与首页数据并行，不阻塞；结果只落红点，不弹窗打断。
- 同一设备 6 小时内不重复查（本地记 `lastCheckAt`）。
- 有更新时：设置页红点常驻 + 一条可关闭的 toast；用户点进去才看到版本说明和「立即更新」。
- 用户点「稍后」→ 本地记住「已提示到此版本」，不再重复弹，但红点保留。
- 「设置 → 关于 → 检查更新」随时可强制查。

### 13.4 强制更新

只在安全问题时用：清单里 `critical: true` + `minVersion`，服务端启动时直接拒绝低版本客户端连接并给出升级入口。默认不启用——个人 NAS 场景，用户被锁在门外比漏洞风险更让人恼火。

## 14. 分阶段落地（直接做增量，不走全量过渡）

按依赖顺序，四步。**每一步都能独立验收，不要求前一步上线才能开始下一步。**

| 步骤 | 做什么 | 工作量 | 验收标准 |
| --- | --- | --- | --- |
| **① 发布侧**（地基） | `tool/release/manifest.js`（版本目录 → manifest + ed25519 签名）、`delta.js`（`from[]` → bundle + brotli + 逐文件 sha256）、`publish.js`（GitCode 两步上传 + GitHub + Gitee + 回读校验）、`update.json` 生成 | 2 天 | 对真实 1.3.13 目录跑一次，产出 2~4 MB 增量包；`curl -I` 回读全 200；`update-delta-smoke` 能解包校验 |
| **② 服务端**（核心） | 拆壳（内核从 `versions/current` fork）+ `runtime/node_modules` + 下载器（多源 + 续传）+ 硬链接组装 + 验签 + 切指针 + `boot.json` 自愈 + 回滚 + `check/install/rollback` 契约 + DB 快照 | 4 天 | 真机 1.3.12 → 1.3.13 增量 3 MB / 40 秒内完成；kill 掉新版本进程 3 次能自动回滚且数据可读；`smoke:updater` 扩到 20+ 项 |
| **③ 客户端三端** | 登录时检查 + 设置页更新区块（进度 / 取消 / 稍后 / 手动检查）+ PC 静默安装（`COLANAS_RELAUNCH`）+ 便携版引导器 + Android 下载/验签/安装 Intent/权限引导 + TV 焦点适配 | 4 天 | PC 点一下更新到重启回来 ≤ 60 秒；小米/华为真机走通「下载 → 授权 → 安装」；换源在弱网下自动发生 |
| **④ 收尾** | 离线包（`update/inbox`）+ 服务端「已更新请刷新」推送 + 旧版本清理策略 + `channel: beta` | 2 天 | 断网环境用 U 盘包完成更新；Web 标签页收到刷新提示 |

**总工作量约 12 天**，其中 ①② 是必须按顺序的，③ 可以在 ② 后期并行开工。

**为什么不先做一个「全量更新过渡版」**：全量路径（下载 551 MB setup → `/S`）所需的组件——清单、下载器、校验、重启——在增量方案里全都要重写一遍（增量是「组装目录 + 切指针」，不是「跑安装器」）。先做全量等于写两套然后扔掉一套。**唯一保留的全量逻辑**：增量包 404 / 校验不过 / 基线不在 `from[]` 里时，自动回退到全量安装包，作为 `install` 接口里的一条降级分支。

**增量失败的降级路径**（必须在 ② 里一起做）：增量包 404 / 校验不过 / 基线版本不在 `from[]` 里 → 自动回退到全量安装包。所以全量下载能力不是白写的，它是兜底。

## 17. 需要拍板的事

已经定下来的（写进方案，不再讨论）：服务端默认不自动更新、客户端登录时检查、直接做增量、默认 GitCode 太慢切 GitHub、客户端不做增量。

剩下的只有三件：

1. **GitCode 账号开通 + 实测直链 ACL**。这是唯一还有不确定性的环节：`upload_url` 返回的 `x-obs-acl` 是 `public-read` 还是 `private` 决定直链能不能匿名下载。开通后先手动传一个 551 MB 的包，`curl -I` 验一次，30 秒的事，能把整条链路的假设证伪。
2. **Windows 代码签名证书**要不要买（约 1000~3000 元/年）。没有它，SmartScreen 会对每个新版本弹「未知发布者」，静默安装尤其明显。签名清单解决的是「内容没被改」，解决不了「这个 exe 是谁发的」。
3. **PC 客户端要不要同时支持便携版**。便携版要多写一个几十 KB 的引导器（`ColaNasOs.exe` 读 `current.txt` 加载新目录）。如果你只发安装版，这一块可以先不做，省 1 天。

### 18.2 与原方案的差异（都是实现时不得不改的）

1. **增量资产名是扁平的**（`0-main.dart.js.br` / `smallfiles-<sha12>.brb` / `manifest-D10314.json`），
   不再用 `urlBase + path` 拼。原因：Release 资产不能带目录，GitCode/GitHub/Gitee 都会把 `/` 拍平。
   协议里因此给 `delta.files[]` / `bundles[]` 加了可选 `urls`（有就用，没有才回退到 `urlBase + 名字`）。
2. **离线包是目录不是 zip**：`update/inbox/colanas-offline-<ver>/`（内含 `update.json` + `.sig` + `files/`）。
   解 zip 要引依赖，而「把文件夹拷进 inbox」对用户一样简单；导入走的校验/组装/切指针与在线完全同一条路径。
3. **`from` 是变化文件的并集**：一份清单只有一份文件列表，若某文件相对 A 变了、相对 B 没变，
   它仍必须出现（否则从 A 升上来的会漏文件）。对 B 的用户只是多下一份同样的文件。
4. **检查失败返回 200 + `error` 字段**，不返回 5xx。内网 NAS 离线是常态，
   把「检查不到」变成报错日志没有意义；界面按 `error` 显示「稍后重试」。
5. **自动检查定时器只刷清单缓存**（默认关）。真正安装永远是用户点。

### 18.3 踩到的坑（写下来免得再踩）

- **`undici.request` / `fetch` + `AbortController` 会把内核打崩**：读 body 期间 abort，
  或 HTTP/1.0 响应（`python -m http.server`）在背压下被暂停时，undici 抛
  `AssertionError: assert(!this.paused)`，整个进程 exit。解决：`fetch` + `getReader()` 手工抽干，
  熔断改 `reader.cancel()`；落盘用**同步写**（`fs.writeSync`），避免两次 read 之间留异步间隙造成背压。
- **硬链接不能原地写**：`unlink` 再 `copyFileSync`，否则会把旧版本的文件一起改掉。
- **`version.json` 不能覆盖**：它在清单里，发布产物写什么就是什么，重新写会让切指针前的全量校验对不上。
- **播种必须逐文件复制**：打包态源码在 `app.asar` 里，`fs.cpSync` 走底层 copyfile 不经 asar 补丁。
- **签名密钥**：私钥在 `.keys/update-signing.pem`（已被 `*.pem` 忽略）或
  `%USERPROFILE%\.colanas\deploy.pem`，也可用 `COLANAS_SIGN_KEY` 指定。**务必备份**，
  丢了就没法给已发布版本发增量（只能让用户重装换公钥）。

### 18.4 一次真实发版怎么走

```bash
npm run build && build-web.bat                 # 编译内核与 Web
node tool/release/release.js \
  --out=dist_release --tag=v1.3.14 \
  --from=dist_release/D10313 \                 # 基线目录（保留上一版的 dist_release）
  --url-base=https://gitcode.com/colaKot/ColaNasOs/releases/download/v1.3.14,\
https://github.com/colaKot/ColaNasOs/releases/download/v1.3.14 \
  --setup=dist_installer/ColaNasOs-Server-1.3.14-Setup.exe \
  --pc-setup=dist_installer/ColaNasOs-Client-1.3.14-Setup.exe \
  --apk=dist_installer/ColaNasOs-Client-1.3.14-android-arm64.apk \
  --notes-zh="修复…"
node tool/release/publish.js --dir=dist_release --tag=v1.3.14   # 先资产后清单，末尾回读
node tool/release/offline.js --dir=dist_release                  # 需要离线包时
```

服务端与客户端的清单地址默认是 `…/releases/download/update-stable/update.json`
（GitCode / Gitee）与 `…/releases/latest/download/update.json`（GitHub），
可在「设置 → 更新 → 清单地址」或 `COLANAS_UPDATE_MANIFEST` 覆盖。

### 18.5 还没做的（明确留白）

- **Web 标签页「已更新请刷新」推送**（§8.5）：目前靠用户自己刷新。SSE 已有通道，接一条消息即可。
- **上传前的发布后回读**只在 `publish.js` 里做了 HEAD 校验；GitCode 的 ACL 是否 `public-read`
  仍需第一次真实上传后人工确认一次（方案 §17 第 1 条）。
- **Windows 代码签名证书**（§17 第 2 条）：没有它 SmartScreen 仍会对新安装包提示未知发布者。
- **便携版自替换引导器**（§8.3）：只实现了安装版静默更新。
