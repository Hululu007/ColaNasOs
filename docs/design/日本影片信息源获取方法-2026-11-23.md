## 0. 结论先说

调研了 5 个开源项目的抓取实现，抛开成品形态，它们在「怎么拿到准确信息」上高度一致，核心是三条：

1. **以番号为唯一主键做精确查询**，绝不拿文件名/标题去做模糊匹配。当前电影2 库的错配（番号 `SIRO-1690` 被刮成意大利纪录片《圣西罗》）根因就是把番号当普通片名丢给了 TMDB 做模糊搜索。
2. **多数据源按优先级串接、命中即停**，而不是单源硬查或全源 fan-out。官方接口优先于网页抓取，网页抓取优先于联邦聚合。
3. **拿到结果后做一致性校验**（番号回文、地区、发行日期、演员/片商），不合格就换下一个源——这是防止「串台」（A 番号挂了 B 的标题）的关键，也是现有 NFO 最缺的一环。

要补的信息获取能力 = **番号精确查询 + 源优先级链 + 反爬韧性 + 结果校验**，四者缺一不可。成品应用不必接，这套方法可以直接自建。

## 2. 数据源图谱：信息到底从哪里来

把 5 个项目实际连接的站点按「权威性 / 获取方式」归三类。这是整套方法的基础——先知道哪些源可信、怎么取。

### 2.1 官方 / 半官方结构化接口（首选，字段最干净）

| 源 | 入口 | 获取方式 | 特点 |
| --- | --- | --- | --- |
| **DMM** | `https://api.video.dmm.co.jp/graphql` | 官方 GraphQL，失败降级 HTML | 数据最权威；**需日本 IP**；封面无水印 |
| **JavDB App** | `jdforrepam.com` / `javdb.com` | 签名接口，生成 `jdsignature`，UA 伪装 `Dart/3.4` | 字段全、无水印；签名失效自动降级网页；重复关键词会触发 CF 封禁 |
| **r18dev** | `https://r18.dev/videos/vod/movies/detail/-/combined=%s/json` | JSON API + 限流 + 重试，尊重 429 `Retry-After` | 无需网页解析、最稳；覆盖率中等；默认源 |
| **FC2 / FANZA** | 官方站 | 结构化页面 / 官方接口 | 发行日期准确；FC2 多为素人番号 |

### 2.2 网页抓取（覆盖面最广，需反爬）

`JavBus`、`JavDB` 网页版、`jav321`、`mgstage`、`heyzo`、`caribbeancom`、`sokmil`、`avbase`、`avwikidb`、`prestige`、`dahlia`、`faleno`、`km_produce`、`fc2` 等。

- 抓取方式：detail 页直取（番号 → 固定 URL 模式），或 keyword 搜索。
- 典型陷阱：JavBus 的 `/search/` 端点返回 200 而非 404（空结果是页面而非错误）；jav321 的 keyword 搜索恒空；mgstage 需年龄验证 cookie `adc=1`。
- 部分源封面带水印、无简介、无评分——能力的差异需要在源层标记。

### 2.3 联邦 / 聚合（兜底，不精确）

- **MetaTube**：联邦网关，可挂 30+ provider；JvedioNext 本身就是它的纯消费方。
- **JavStash**：GraphQL，需 API key。
- 定位：前面都查不到时的兜底，不适合当主源（结果一致性差）。

### 2.4 对照：现有 discover 模块的能力边界

`src/modules/discover/index.ts` 当前只做离线 NFO 解析（`parseNfo` 正则取扁平字段）+ 豆瓣/TMDB 榜单。**TMDB/豆瓣没有 JAV 结构化数据**，这正是错配的来源——它们擅长普通电影，不擅长番号。日本信息必须走上面 2.1 / 2.2 的源。

## 3. 获取方式：六条可复用的方法

这部分是文档核心——「怎么稳定地拿到正确信息」。

### 3.1 精确查询优先，模糊搜索兜底

番号是强结构化标识（`ABP-376`、`FC2-PPV-3260300`、`MIAD-00812`），应该直接拼 detail URL 或走 `q=<番号>` 精确接口。所有调研项目都把「exact」设为默认，模糊搜索（按演员、部分关键词）只在精确无果时启用，且单独隔离。

> 直接对应我们的错配：`SIRO-1690` 若走精确接口，拿到的必然是对应番号的结构化数据，不会是 TMDB 里的同名纪录片。

### 3.2 源优先级串接，命中即回

不是 fan-out 全源并发（实测 10~24s），而是按「精确命中率 × 数据质量 × 可用性」排序后逐个尝试，命中即返回（实测 1~2.3s）。一个典型优先级：

```
DMM 官方 API → JavDB 签名 API → r18dev JSON → JavBus 网页 → jav321 → MGStage → 联邦兜底
```

每源带能力标记：是否支持精确 / 模糊、是否需日本 IP、封面是否带水印、是否有评分/简介。调度时按标记跳过不适用的源。

### 3.3 反爬韧性：四件套

| 手段 | 作用 | 出处做法 |
| --- | --- | --- |
| Cookie 持久化 + 按站隔离 | 维持会话、年龄验证 | `InMemoryCookieJar`，按 site 分开存 |
| 代理按站分流 | DMM 等需日本 IP；其它站避开被封网段 | 配置层声明每站 proxy |
| 限速 + 退避 | 避免触发封禁 | 默认每站间隔 3s；识别 429 的 `Retry-After` |
| Cloudflare 挑战升级 | 网页被 CF 拦时自动过验证 | FlareSolverr，拿到 cookie 后回写并回落直连 |

还有一个细节值得学：**把失败分类**（`region_blocked` / `ip_banned` / `login_required` / `parse_error`）。区分「本源暂时不可用」和「番号真的不存在」，才能正确决定是换源还是终止。

### 3.4 降级链

每个源都要有下一级：`官方 API 失败 → HTML 抓取 → 换源 → 联邦兜底 → 标记 none`。绝不能单源失败就写空——现在的 5 条缺失就是这么来的。

### 3.5 结果一致性校验（防串台的关键）

拿到结果后，写入前必须校验：

1. **番号回文**：返回的番号/标题里必须能找到查询的番号（归一后比较，忽略补零差异 `MIAD-738` ≡ `MIAD-00812`）。`MIAB-437` 挂 `ABW-173` 这种直接判失败、换源。
2. **地区校验**：地区应为 Japan/日本；出现 Italy / Italy+纪录片导演 = 立刻拒绝（《圣西罗》就是这么拦下来的）。
3. **日期合理性**：年份落在合理区间（如 1990~当前+1），且和番号里的年份线索不冲突。
4. **演员/片商一致性**：多源结果交叉比对，差异过大则标记待核，不自动覆盖。

### 3.6 只补空、不覆盖

写入策略：新数据只填当前为空的字段，已有且非空的 NFO 字段保留。这样即使新源猜错，也不会破坏用户已有的正确数据——比"重刮覆盖"安全得多。

## 4. 数据模型：要拿哪些字段

各项目的字段高度趋同，收敛成一份「最小完备集」即可覆盖 jp_movie 展示所需：

| 字段 | 用途 | 备注 |
| --- | --- | --- |
| `number` | 番号（主键） | 必须回文校验 |

| `actresses[]` | 演员 | 已有角标 / 演员页要用 |
| `maker` / `publisher` / `label` / `series` | 片商 / 发行 / 厂牌 / 系列 | 目前 NFO 里大多为空，是主要补齐项 |
| `director` | 导演 | |
| `release_date` | 发行日期 | YYYY-MM-DD；校验合理性 |
| `genres[]` | 标签 | |
| `cover_url` / `poster_url` / `fanart_url` | 封面 / 海报 / 背景 | 标记是否带水印 |

## 5. 自建落点建议（不改代码，仅方案）

若要落地，建议形态：

- 在 `src/modules/discover/` 下新增独立的 JAV provider，与现有 NFO / 豆瓣 / TMDB 并列，互不干扰。
- 配置项：源开关、优先级、每源代理与 cookie、限速间隔、FlareSolverr 地址（可选）。沿用项目「没有 key 就不注册、不静默失败」的原则——没配源就不启用这条能力，而不是假装成功。
- 触发时机：扫描时 `nfo_source=none` 或番号回文校验失败的条目，才进入 JAV 查询链；已有正确 NFO 的不动。
- 查询结果写入独立表（或扩 `video_meta`），遵循 3.6「只补空不覆盖」。
- 可复用的现成数据：`OpenAver` 的 `dmm_prefix_table.json`、`maker_mapping.json`（番号前缀 → 片商映射），能直接提升片商字段的完整度。

**为什么不接成品**：五个项目里，两个不开源（JvedioNext 只有文档、sakuramedia 抓取代码在另一个仓库且禁商用），其余三个分别是 Python / Go / Electron 形态，接进来等于引入一整套异构服务。而它们真正有价值的部分——数据源清单、抓取手法、校验规则——是可以直接用本项目技术栈重写的知识，不需要背负成品的运维成本。

## 6. 风险与边界

- **许可证**：OpenAver、javinizer-go 是 MIT；mdcz 是 GPLv3（与本项目 GPL-3.0 兼容，但其 README 另有「勿商业化」声明）；sakuramedia 是 PolyForm Noncommercial（禁商用，已排除）。**借鉴方法不受影响，复制源码需注意许可证**。
- **地区 IP**：DMM 官方接口对日本 IP 覆盖最全；**实测台湾出口 IP 也能查到部分有码番号**（SONE-205 命中），但无码/素人番号查不到——这部分是 DMM 片库本身没有，不一定全是 IP 问题。其它站多有地域策略（详见 §8）。
- **封号风险**：JavDB 等站对频繁/重复查询敏感，需限速、避免同一关键词反复打、建议用小号。
- **上游不稳定**：网页结构随时变、签名会失效——所以降级链和失败分类是必需品，不是可选项。
- **内容边界**：本方法只用于个人 NAS 库的元数据整理（番号、演员、片商、日期等结构化信息），不涉及任何内容分发。

## 8. 实网验证（2026-11-23，针对问题番号）

前面是方法推演，这节是**真网络实测**：拿电影2 库里那几条问題番号，逐个试各获取方式，看谁真能拿到正确信息。测试环境：本地代理出口 `36.230.21.140`（中国台湾，非日本）。

### 8.1 各方式实测结果

| 方式 | 连通性 | 能否拿到问题番号 | 结论 |
| --- | --- | --- | --- |
| **JavDB 网页搜索** `javdb.com/search?q=<番号>` | 通，但连续请求后 **403 封 IP** | ✅ **能**。实测拿到 `SIRO-1690`、`MIAB-437` 的正确标题/日期/评分/封面 | **最有效，但必须低频 + 备用源**；首两次请求成功，之后整段被封 |
| **DMM 官方 GraphQL** `api.video.dmm.co.jp/graphql` | ✅ 通（无需日本 IP） | ⚠️ **部分**。有码番号 `SONE-205` 命中 2 条；`SIRO-1690`/`MIAB-437` 返回 0（无码/素人片库本身没有） | 官方字段最干净，覆盖有码片；无码要靠别的源 |
| **JavDB App 签名接口** `/api/v2/search` + `jdsignature` | 通，接口正常返回 JSON | ❌ **需登录**：`JWTVerificationError: 請登錄帳號` | 签名算法仍有效，但 **2026 年已加登录墙**，无账号不可用 |
| **r18dev JSON API** `r18.dev/.../combined=<番号>/json` | 首页 200，API 路径被 **Cloudflare 拦** | ❌ 拿不到 | 文档里的"默认最稳源"在当前出口下不可用 |
| **JavBus 网页** `javbus.com/<番号>` | 通，但 Taiwan IP 触发**年龄验证墙** | ❌ 拿不到 | 表单 POST 未过（服务端按 IP 判定 + 需 token），需 cookie/换出口 |
| **jav321** `jav321.com/search?sn=<番号>` | 通 | ❌ 查无：`AVが見つかりませんでした` | 印证 OpenAver 文档"jav321 keyword 恒空" |
| **mgstage / javlibrary** | 403 | ❌ | 地域/Cloudflare 限制 |

### 8.2 关键证据：JavDB 拿到的正确数据

```
番号 SIRO-1690
  库里现有 NFO : 圣西罗 / 地区 Italy / 2014  ← 错（意大利纪录片）
  JavDB 实测   : "SIRO-1690 素人個人撮影、投稿。503" / 2013-11-24 / 4.5 分  ← 正确

番号 MIAB-437
  库里现有 NFO : "ABW-173 天然成分由来 七嶋舞汁…"  ← 错（串台到 ABW-173）
  JavDB 实测   : "MIAB-437 〈百合カップル男根堕ち〉…天馬ゆい 柏木こなつ（BOD）" / 2025-01-21  ← 正确
```

### 8.3 校验规则实测有效

用 §3.5 的**番号回文校验**跑一遍：

| 番号 | 库里现有 NFO 校验 | JavDB 结果校验 |
| --- | --- | --- |
| SIRO-1690 | **FAIL** ← 自动识别为错配 | PASS |
| MIAB-437 | **FAIL** ← 自动识别为串台 | PASS |

即：**不联网也能先把库里错的挑出来**（回文 FAIL + 地区非 Japan），再用 JavDB/DMM 逐条补正确数据——这正是 §5 建议的触发时机（"校验失败的条目才进查询链"），实测可行。

### 8.4 对方案的修正

1. **JavDB 是这批无码番号唯一实测拿到数据的源**，但它一封就全封——自建时必须把它当"低频精查源"（每条间隔数秒、失败即退避），不能当批量刮削源。
2. **DMM GraphQL 无需日本 IP 也能用**（修正 §6 旧表述），适合有码片批量补；无码片另找源。
3. **App 签名接口已加登录墙**，文档里"签名绕 CF"的现状已变，这条降级路径按未登录处理。
4. **r18dev / JavBus / jav321 在当前出口下都拿不到**——多源不是备着好看的，实测确实只有 1~2 个源能用，所以失败分类和降级链是刚需。
