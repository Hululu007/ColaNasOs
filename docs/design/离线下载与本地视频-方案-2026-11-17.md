> 目标平台：Windows 客户端、Android 客户端。服务端只跑 Windows 单机内核。

## 0. 结论

1. 需求书里「用现有 Flutter SQLite + Drift」的前提**不成立** —— 客户端没有 Drift、没有任何本地数据库，只有 `SettingsStore`（JSON 文件 / localStorage）。本地索引要重新选型（见 §11 D1）。
2. 「编码 / 分辨率 / 码率联动」**已经被播放链路解决**：`contracts/play-quality.json` 里有 `presets[].bitrates{ h264, h265, av1 }` 的完整表，且已生成到 Dart（`core/play_quality.dart`）与 TS（`videoPlayer/play-quality.generated.ts`）。下载弹窗直接吃这张表，两边算出来的数字天然一致，不需要新表、不需要新算法。
3. 真正要新建的只有四块：**服务端 `offline-download` 模块**、**media sidecar 的 `encode` 操作**（单文件成品 + 进度 + 取消）、**客户端下载执行器**、**客户端本地媒体库**。其余（Range 续传、任务队列、后台前台服务、多选组件、画质表）全部能复用现成实现。

## 2. 数据模型

### 2.1 服务端（SQLite，内核 `migrations`）

两张表，跟 HLS 会话表同级，**不碰 `video_items`**。

```sql
-- 编码任务（客户端可见的 job）
create table if not exists offline_jobs (
  id            text primary key,          -- uuid
  task_id       text not null,             -- kernel/queue.ts 的 tasks.id
  item_id       text not null,             -- video_items.id
  library_id    text not null,
  series_key    text,                      -- 剧集聚合键 = library_id + '\u0000' + series
  params        text not null,             -- 参数指纹（见下）
  spec          text not null,             -- 目标参数 JSON（codec/height/bitrate/audio/sub/container）
  operation     text not null,             -- create | replace（仅语义标记，服务端行为一致）
  artifact_id   text,                      -- 完成后指向 offline_artifacts.id
  state         text not null,             -- queued | transcoding | ready | failed | canceled
  progress      real not null default 0,   -- 0..100
  error         text,
  created_at    integer not null,
  updated_at    integer not null
);
-- 同一源视频 + 同一套参数，只允许一个活动任务
--
-- 唯一性口径是 (item_id, cache_key) 而**不是** item_id：「同一部电影只留一个本地版本」
-- 是**设备级**约束（由客户端保证）；服务端这里只负责「别为同一份产物重复转码」。
-- 两台设备同时要 1080p 和 720p 是合理需求，按 item_id 唯一会直接把第二台 409 掉。
create unique index if not exists ux_offline_jobs_active
  on offline_jobs (item_id, cache_key)
  where state in ('queued','transcoding');

-- 编码产物（按参数指纹去重，多设备共用同一份）
create table if not exists offline_artifacts (
  id          text primary key,            -- uuid
  cache_key   text not null unique,        -- sha1(item_id|codec|height|kbps|audio|sub|container)
  rel_path    text not null,               -- dataDir/offline/artifacts/<cache_key>/<name>
  size        integer not null,
  sha256      text not null,
  etag        text not null,               -- 尺寸+mtime，复用 files/download.ts#etagOf
  mime        text not null,
  width       integer, height integer,     -- 实际产出规格（不是请求值）
  duration_ms integer,
  video_codec text, audio_codec text, bitrate integer,
  state       text not null,               -- active | deleting | missing
  ref_count   integer not null default 0,  -- 有多少 job 在用（>0 不回收）
  created_at  integer not null,
  last_hit_at integer not null
);
```

**参数指纹**（`cache_key`）决定「同参数是否复用」：

```
sha1(item_id | codec | height | videoKbps | audioIndex | audioKbps | subtitleMode | container)
```

同一部电影，两个人/两台设备选同样参数 → 只编一次。

**产物目录**：

```
<dataDir>/offline/
  artifacts/<cache_key>/
    out.mp4            # 转码档
    out.mkv            # 原画 remux
    meta.json          # 探测结果 + sha256 + 参数（产物的唯一真源）
```

### 2.2 客户端（设备本地，见 §11 D1 推荐方案）

**不做数据库**，用「清单 JSON + 原子写 + 启动对账」。理由：离线媒体本来就以文件为真相，清单只是索引；清单丢了可以从 `videos/` 重建（`meta.json` 在片旁边），数据库坏了反而要写迁移。

```
Offline/                        # PC: 用户可选目录；Android: getExternalStorageDirectory()/Offline
  videos/<itemId>.<ext>
  posters/<sha1>.jpg
  backdrops/<sha1>.jpg
  subtitles/<itemId>.<lang>.srt
  temp/                         # 必须与 videos/ 同卷（保证 rename 原子）
  index/
    groups.json                 # 合集：[{ id, libraryId, seriesKey, kind, title, posterSha, totalEpisodes, itemIds[] }]
    items.json                  # 条目：[{ id, groupId, sourceKey, sourcePath, title, season, episode, spec{...}, bytes, posterSha, downloadedAt, playbackMs, sourceMissing }]
    tasks.json                  # 未完成下载：[{ id, itemId, groupId, artifact{...}, tempPath, downloadedBytes, etag, sha256, state, error, createdAt }]
    replace.log                 # 替换日志（崩溃恢复，写一次删一次）
  .nomedia
```

写盘规则：一律「写 `x.json.tmp` → `rename` 覆盖」，避免半截 JSON。列表规模按 5000 条估（单条约 400 B ≈ 2 MB），内存里做分组/排序/筛选足够。

**索引与文件的对账**（每次启动 + 每次进入本地视频页）：

1. `items.json` 里 path 不存在的 → 标 `missing`，不删记录；
2. `videos/` 里有文件但索引没有 → 读 `meta.json`（写在片同目录）恢复，恢复不了就忽略；
3. `posters/` 里没被任何 group/item 引用的 → 删（引用计数用 JSON 里数，不用单独表）。

### 2.3 身份与唯一键

| 对象 | 唯一键 | 说明 |
| --- | --- | --- |
| 电影本地条目 | `sourceKey = video_items.id` | 一台设备一部电影一条 |
| 电视剧本地条目 | `sourceKey = video_items.id`（= 单集） | 一集一条 |
| 剧集合集 | `seriesKey = libraryId + '\u0000' + series` | **下一集也落同一个 group**，满足「下了一集也有整剧封面」 |
| 下载任务（客户端） | `itemId`（`tasks.json` 里 itemId 唯一） | 替代需求书的「同一视频只有一个活动任务」 |
| 编码产物（服务端） | `cache_key` | 多设备复用 |

> 为什么合集键不用 `series` 单字段：不同库可能有同名剧（一个 `series` 名在不同 `library_id` 下是两部剧）。

## 3. 接口设计

新模块 `src/modules/offline-download/`，prefix `/api/v1/offline-downloads`，权限复用 `video:read` / `video:write`（不新增 scope）。

纳入现有链路：TypeBox → `openapi.json` → Dart client（`npm run gen:client`）+ i18n（`gen:i18n`）。

### 3.1 `POST /quote` — 参数推荐与校验

```
入: { itemId, codec?, height?, qualityMode?, videoKbps?, audioIndex?, audioKbps?, subtitleMode? }
出: {
  source: { width, height, videoCodec, audioCodec, durationMs, bytes, bitrateKbps, hasHdr, dvProfile?, is4k }
  capabilities: { codecs: ['h264','h265','av1'], heights: [1080,720,480], hwEncoders: ['amf','nvenc'] }
  target: { codec, height, videoKbps, audioKbps, container, subtitleMode }
  limits: { minKbps, maxKbps, recommendedKbps }
  estimate: { bytes, seconds }        // seconds 用「本机实测吞吐」估，没测过就不给
  actions: { downloadedBytes?, activeJobId?, existingSpec? }   // 已下载/正在下载时回填
}
```

联动规则落在**服务端**（客户端只是同步显示，避免两端算法漂移）：

1. 换 codec → `recommendedKbps = play-quality.presets[matched].bitrates[codec]`；
2. 换分辨率 → 选该高度的档位再取 codec 列；
3. `qualityMode = saver | standard | high` → 取 `0.6x / 1.0x / 1.8x` 夹到 `[min,max]`；
4. 用户手填 `videoKbps` → 原样保留，只做 `[min,max]` 夹取；
5. `codec = original` → 锁死 codec/height/kbps，容器按源文件走。

`min/max` 取推荐值的 `0.4x ~ 2.5x`，且 `min` 不低于 `120 kbps`。

### 3.2 `POST /jobs` — 创建

```
入: { itemId, spec{...}, operation: 'create'|'replace', idempotencyKey }
出: { id, state, progress, artifact? }
```

- 已有活动任务（`ux_offline_jobs_active` 命中）→ **返回该任务**，不报错、不重复建（需求书 §3.2 场景 B）；
- 已有完成产物且 `operation = create` → 返回 `409 + { existing }`，让客户端进覆盖确认（场景 A）；
- `operation = replace` → 承认用户已确认，允许建新任务；**旧产物在客户端侧仍可用**（客户端不动旧文件，服务端也不删旧产物，见 §5）。
- `idempotencyKey` 落 `offline_jobs` 的一个隐藏列，重复 POST 直接返回同一条。

内部动作：写 `offline_jobs` → `k.tasks.enqueue('offline.encode', {...}, { maxAttempts: 1, priority: 3 })`。

> `maxAttempts: 1`：整片编码动辄十几分钟，自动重试等于把失败重跑一遍。失败就失败，让用户点重试（重试=新任务）。

### 3.3 `GET /jobs/:id` — 状态

```
出: { id, state, progress, encoder?, speed?, error?, artifact?: { id, size, sha256, etag, mime, spec } }
```

`progress` 来自 sidecar 的进度事件（§4.3），不是猜的。`state` 与 `tasks.state` 的映射在内核里做（`pending→queued`、`running→transcoding`、`done→ready`）。

### 3.4 `POST /jobs/:id/cancel`

kill 当前 ffmpeg（sidecar 按目录精确命中）→ 标 `canceled` → 清临时产物目录。已生成的中间文件一并删。

### 3.5 `GET /artifacts/:id` — 下载文件

套 `files/download.ts` 的语义：`Accept-Ranges: bytes`、`ETag`、`If-Range`、`206`、`416`，外加 `x-artifact-sha256` 头（客户端边下边算，省一次读盘）。

只服务 `offline_artifacts` 里 `state='active'` 的产物，**不接受路径参数**（避免路径穿越；这条是相对 `/files/download?path=` 的唯一区别）。

### 3.6 `DELETE /artifacts/:id`

只清离线模块自己的产物（`artifacts/<cache_key>/`），`ref_count > 0` 时拒绝。**永远不碰服务器原始影视文件。**

## 4. 服务端编码流水线

### 4.1 sidecar 新增 `encode` 操作

`encode({ src, dst, codec, height, videoKbps, audioIndex, audioKbps, subtitleMode, qualityMode, hwaccel, container })`

**与 `hls()` 共用的前半段**（抽成 `resolveEncodePlan()`，两边都调）：

- `probeSourceInfo(src)`：片源真实编码 / HDR / DV profile（不信库里的标记，理由已在 `main.js` 注释里写死）；
- 高度夹取 `min(srcHeight, presetHeight)`，矮片源不放大；
- `hdrToSdr` 判定 + tonemap 链选择（libplacebo / d3d11 / cuda）；
- 编码器候选与降级链（硬编失败 → 软编）；
- 目标码率（`maxrate` + `bufsize`）。

**只有输出尾部不同**：

| 项 | HLS | 单文件 encode |
| --- | --- | --- |
| 视频 | `-c:v <hw或cpu>` | 同 |
| 音频 | 固定 `aac 128k stereo` | `aac` + 可选码率；`audioIndex` 显式 `-map 0:a:N?` |
| 字幕 | `-sn`（烧录走 filter） | `-sn`；`subtitleMode=embed` 时 `-c:s mov_text` |
| 容器 | `-f hls` + fMP4 | `-f mp4` + `-movflags +faststart` |
| HEVC 标记 | `-tag:v hvc1` | 同（**mp4 里不标 hvc1，Android 硬解会失败**） |
| 色彩 | `-color_primaries/-trc/-colorspace bt709` | 同 |
| 进度 | 无（靠分片数推） | `-progress pipe:1 -nostats` → 解析 `out_time_us`（**只信 us，不信 ms**：`out_time_ms` 因历史原因也是微秒） |
| 超时 | 30 min | `durationMs × 6 + 10 min`（4K 软编留余量） |

**原画（`codec = original`）**：不做重编码，`-c copy` remux 到 **mkv**（保留全部音轨与内嵌字幕，Android/PC 的 libmpv 都认）。若源已经是 `mp4 + h264 + aac` 且单音轨无字幕，直接复制文件、不跑 ffmpeg（秒出）。

> 需求书里写「原画锁定编码/分辨率/码率」是对的，但没定容器。选 mkv 而不是 mp4 的理由：mp4 装不了 DTS/PGS/多条音频轨，硬塞就得重编码音频，那就不叫原画了。

### 4.2 与播放转码的资源争抢

这是本模块唯一的运行时风险点。sidecar 的 GPU 零拷贝链全局串行（两路硬件编码会把编码器卡死，`main.js#cancel()` 有实测记录）。

规则（写在 sidecar 里，内核不参与判断）：

1. `activeHls.size > 0` → 本次 encode **强制 CPU 软编**（`allowHw = false`），让播放先走硬件；
2. 空闲时才允许硬件编码；
3. `encode` 全程 `-threads ${max(1, cpus/4)}`，把 CPU 留给播放与扫描；
4. 同一时刻只允许 **1 路** encode（sidecar 内 `encodeLimiter(1)`），排队不占槽。

代价：边看边下时下载慢 2~4 倍。这是有意的取舍 —— 播放是交互式操作，下载不是。

### 4.3 进度事件

sidecar 已有事件通道（`send({type:'event', event, data})` → supervisor `emit('event')`）。

```
event: 'encode_progress'
data:  { dir, file, percent, outTimeMs, totalMs, speed, elapsedMs }
```

节流 500 ms 一条，按 `dir` 过滤（同一 sidecar 可能还有别的任务的事件在路上）。
内核的 task handler 订阅后写 `offline_jobs.progress` + `queue.progress(pct)`，
客户端轮询 `GET /jobs/:id` 即可。

`percent` 的分母是 `probeSourceInfo` 解析出来的 `Duration:`（已加进 `source-probe.js`），
不是文件大小 —— VBR 片源按字节算出来的进度会跳着走，用户看着像卡住。

`percent` 的分母用 `probe` 得到的 `durationMs`（不是文件大小，码率是 VBR，按字节算会跳）。

## 5. 文件生命周期

### 5.1 首次下载

```
1. POST /jobs            → jobId
2. 轮询 GET /jobs/:id    → transcoding (progress)
3. state=ready           → GET /artifacts/:id 拿 size / sha256
4. 检查剩余空间 >= size + 200MB 余量，不够就停（在 temp 里已下的保留）
5. 下载到 temp/<jobId>.part，边下边算 sha256
6. size 与 sha256 与产物元信息比对
7. rename temp/<jobId>.part → videos/<itemId>.<ext>
8. 写 meta.json（与片同目录）、更新 items.json / groups.json（原子写）
9. DELETE /artifacts/:id（服务端产物此刻才允许回收）
```

第 7 步的 `rename` 必须在同一卷内（`temp/` 与 `videos/` 同在 `Offline/`，天然保证）。

### 5.2 覆盖替换（重下）

```
1. 客户端确认弹窗（当前版本 vs 新版本）
2. POST /jobs (operation=replace)
3. 新文件下载到 temp/<jobId>.part（旧文件一动不动，仍可播）
4. 校验通过后：
   a. 写 replace.log { old, nxt, dst, phase: 'staged' }
   b. rename dst → dst.old        （旧片退位，原子）
   c. rename temp → dst           （新片就位，原子）
   d. 更新索引（fileSize/codec/规格/downloadedAt）
   e. 删 dst.old
   f. 删 replace.log
```

任一步失败/断电，下次启动读 `replace.log` 收敛：

| 现场 | 判定 | 动作 |
| --- | --- | --- |
| `dst` 有、`dst.old` 无 | 没开始退位 | 删日志，删 temp |
| `dst` 无、`dst.old` 有、temp 有 | 卡在 b 与 c 之间 | rename temp → dst（c），再走 d/e |
| `dst` 有、`dst.old` 有 | c 完成、e 未完成 | 删 dst.old，保留新片 |
| `dst` 无、`dst.old` 有、temp 无 | temp 被清 | **回滚**：rename dst.old → dst |

**「编码阶段」没有暂停**：`state=transcoding` 时只提供「取消」。取消后进度归零，重来要重新编码。这条要在 UI 上说清楚（需求书 §3.5 的「暂停」只落在传输阶段）。

### 5.3 删除

```
1. 弹确认（"只删本设备离线副本，不影响服务器"）
2. items.json 移除条目（原子写）
3. 删 videos/<itemId>.* 、subtitles/<itemId>.*
4. 若该 item 是 group 最后一集 → 删 group；group 的 posterSha 引用数归零才删 posters/<sha>.jpg
5. 文件删失败（被播放器占用）→ 记 pending_delete，下次启动重试（不阻塞 UI）
```

多选删除 = 逐个走上面流程，最后一次性写索引（避免 N 次 IO）。

### 5.4 服务端产物回收

`sweepOfflineArtifacts()`（进程启动 + 每小时）：

- `ref_count = 0` 且 `last_hit_at` 超过 24h → 删目录 + 删行；
- 目录存在但行不存在 → 超过 24h 删；
- 行存在但目录不存在 → 标 `missing`（客户端下载会 404，届时提示重新编码）。

## 6. 客户端下载执行器

`features/video/offline/offline_download_manager.dart`（单例，形态照 `TransferManager`）：

```dart
class OfflineTask {
  final String jobId;
  final String itemId;
  OfflineTaskState state;   // queued / transcoding / downloading / verifying / replacing / done / failed / canceled
  double transcodeProgress; // 服务端推的 0..1
  int downloaded, total;
  String? error;
}

class OfflineDownloadManager {
  static final instance = ...;
  final ValueNotifier<List<OfflineTask>> tasks;
  Future<void> enqueue(QuoteResult q);   // 先写 tasks.json，再 POST /jobs
  Future<void> pause(String itemId);     // 仅 downloading 阶段有效
  Future<void> resume(String itemId);    // Range 续传
  Future<void> cancel(String itemId);
  Future<void> restore();                // 启动调用：读 tasks.json + 对账
}
```

要点：

- **先落盘再发请求**：`tasks.json` 写完才 POST，崩溃后能恢复；
- **单连接 Range**（不做多线程分片，需求书 §8 明确第一期不实现）；
- 范围断点续传：本地记录 `etag`，续传时带 `If-Range: <etag>`；服务端返回 200（产物变了）就丢弃 `.part` 重下；
- 并发 1~2 个任务（`_concurrency = 2`），其余排队；
- 边下边算 sha256（`crypto` 包已有），不额外读盘；
- 进度上报节流 300 ms，避免 `ValueNotifier` 每包抖动一次。

**网络中断**：`connectivity_plus` 已有，监听回切后自动 resume（与相册备份同一口径）。

## 8. 存储

### 8.1 Android

- 可改（`file_selector` 已有）；
- 改目录 = 迁移：新目录建好后逐条 `rename`（同卷）或 `copy+校验+删源`（跨卷），迁移期间索引标 `migrating`，中断可续；
- 磁盘拔掉/不可写：任务标 `failed(storage_unavailable)`，不删已有文件。

## 11. 已定案（2026-11-17 确认）

| # | 决策 | 结论 | 影响 |
| --- | --- | --- | --- |
| D1 | 客户端本地索引 | **清单 JSON**（`Offline/index/{groups,items,tasks}.json` + 原子写 + 启动对账） | 不引入 Drift；不新增原生依赖；索引可从 `videos/` 重建。§2.2 按此执行 |
| D2 | 原画容器 | **remux 到 mkv**（`-c copy`，保留全部音轨与内嵌字幕） | `encode()` 里 `codec=original` 走 mkv；转码档仍统一 mp4 |
| D3 | 服务端产物 | **按参数指纹复用，TTL 24h** | `offline_artifacts.cache_key` 唯一 + `ref_count`/`last_hit_at` 回收（§2.1 / §5.4） |
| D4 | 下载入口 | **详情页动作条**并列圆按钮，五态显示 | 电影详情 `_actionRow` 加第 4 个圆按钮；剧集只加在单集上 |

**PC 默认下载目录**：取 `<用户视频目录>/ColaNasOs`（`path_provider.getDownloadsDirectory()` 取不到时退 `getApplicationSupportDirectory()/Offline`），设置页可改。Windows 资源管理器「视频」里能直接看到，符合「下载完能自己找到文件」的直觉。

被否掉的备选（留档，别再翻）：

- Drift + SQLite：6 端要处理原生库，本次只有 PC+Android 用得上，且与「文件即真相」容易不一致；
- 原画统一 mp4：DTS/AC3 要转 AAC、PGS 字幕要丢，名不副实；
- 每任务独立产物：同一部 4K 片看两次编两次，浪费；
- 下载入口只放「更多」：多一层，发现性差。
